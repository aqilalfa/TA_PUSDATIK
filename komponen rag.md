# Komponen RAG SPBE Saat Ini

| No | Komponen | Implementasi / File Utama | Konfigurasi Saat Ini | Fungsi dalam Pipeline | Alasan Pemilihan |
|---:|---|---|---|---|---|
| 1 | **LLM / Generator Jawaban** | `backend/app/core/rag/engine/llm_client.py`, `backend/app/config.py`, `backend/app/api/routes/models.py` | Default runtime via Ollama. Fallback model: `qwen3:4b`. Konfigurasi legacy file model: `Qwen2.5-7B-Instruct-Q4_K_M.gguf`, `MODEL_N_CTX=4096`, `MODEL_TEMP=0.1`, `MODEL_TOP_P=0.95`, `MODEL_TOP_K=40`, `MODEL_MAX_TOKENS=2048` | Menghasilkan jawaban akhir berdasarkan konteks retrieval yang sudah diformat. | Qwen dipilih karena cukup kuat untuk Bahasa Indonesia dan reasoning regulasi, masih feasible untuk hardware lokal. Temperatur rendah `0.1` dipilih agar jawaban lebih deterministik dan tidak terlalu kreatif untuk domain hukum/SPBE. |
| 2 | **Embedding Model** | `backend/app/config.py`, `backend/app/core/rag/langchain_engine.py` | `EMBEDDING_MODEL_NAME = "firqaaa/indo-sentence-bert-base"`, `EMBEDDING_DEVICE="cpu"`, `EMBEDDING_BATCH_SIZE=32`, cache: `/app/models/embeddings` | Mengubah query dan chunk dokumen menjadi vector embedding untuk semantic search. | Model embedding Bahasa Indonesia dipilih agar pencarian semantik lebih cocok dengan dokumen SPBE/regulasi berbahasa Indonesia. CPU dipakai agar lebih kompatibel dan stabil di environment lokal. |
| 3 | **Vector Database** | `backend/app/core/rag/langchain_engine.py`, `backend/app/config.py` | Qdrant di `http://localhost:6333`, collection: `document_chunks`, content payload key: `text` | Menyimpan dan mencari chunk dokumen secara semantik berbasis vector similarity. | Qdrant dipilih karena ringan, cepat, mudah dijalankan via Docker, dan mendukung metadata payload/filter yang penting untuk LLM08 access control. |
| 4 | **BM25 Keyword Index** | `backend/app/core/rag/langchain_engine.py`, `backend/app/core/ingestion/document_manager.py` | File index: `backend/data/bm25_index.pkl`, `BM25_TOP_K=12`, dibangun dengan `rank_bm25.BM25Okapi` | Melakukan pencarian berbasis kata kunci/literal. | BM25 penting karena dokumen hukum sering membutuhkan pencocokan literal seperti nomor pasal, ayat, tabel, indikator, dan istilah regulasi yang kadang gagal jika hanya memakai vector search. |
| 5 | **Hybrid Retriever** | `backend/app/core/rag/engine/retrievers.py`, `backend/app/core/rag/langchain_engine.py` | Jalur retrieval: Qdrant vector search + BM25 search + table literal search + indicator literal search | Mengambil kandidat konteks dari beberapa jalur pencarian sekaligus. | Hybrid retrieval dipilih karena query SPBE bisa bersifat semantik maupun literal. Vector search bagus untuk makna, BM25/literal search bagus untuk istilah teknis dan nomor regulasi. |
| 6 | **Query Classification** | `backend/app/core/rag/langchain_engine.py` | `classify_query(query)`, tipe penting: `table`, `indikator`, dan query umum/legal | Mengidentifikasi jenis pertanyaan sebelum retrieval. | Dipakai agar sistem bisa memperluas kandidat untuk query yang rawan miss, terutama query tabel dan indikator. |
| 7 | **Query Expansion** | `backend/app/core/rag/prompts.py` | `expand_query(query)`, ekspansi konservatif untuk istilah seperti `SPBE`, `TIK`, `BSSN`, `IPPD`, serta anchor untuk pasal/tabel | Membuat varian query tanpa mengubah maksud asli. | Dipilih untuk meningkatkan recall, terutama pada singkatan dan istilah hukum. Ekspansinya konservatif agar tidak menggeser makna legal. |
| 8 | **Parallel Search Strategy** | `backend/app/core/rag/langchain_engine.py` | Untuk setiap query variant, sistem menjalankan vector search, BM25 search, table literal search, dan indicator literal search. `candidate_k = max(k * 3, 15)` | Mengumpulkan kandidat dari banyak jalur sebelum fusion. | Dipakai agar sistem tidak bergantung pada satu jenis retrieval saja. Ini meningkatkan peluang menemukan chunk yang tepat untuk query regulasi yang kompleks. |
| 9 | **Reciprocal Rank Fusion / RRF** | `backend/app/core/rag/engine/rankers.py` | `rrf_fusion(ranked_lists, max_candidates, k=60)` dengan formula `1 / (k + rank + 1)` | Menggabungkan hasil dari vector, BM25, dan literal search menjadi satu daftar kandidat. | RRF dipilih karena sederhana, stabil, dan efektif untuk menggabungkan beberapa ranking tanpa perlu kalibrasi skor antar retriever yang berbeda. |
| 10 | **Context Stitching** | `backend/app/core/rag/engine/context_stitching.py`, `backend/app/core/rag/langchain_engine.py` | Mengambil chunk tetangga ±1 dari Qdrant untuk dokumen yang relevan. | Menyatukan konteks sebelum/sesudah chunk utama agar informasi tidak terpotong. | Dipilih karena dokumen hukum dan audit sering terpecah antar chunk. Stitching membantu LLM menerima konteks yang lebih utuh, terutama untuk pasal, daftar, dan tabel. |
| 11 | **Final Reranking** | `backend/app/core/rag/engine/rankers.py` | `RAGRanker.rerank(query, docs, top_k)`. Mendukung CrossEncoder jika tersedia; fallback memakai `rrf_score`. | Menentukan dokumen final yang masuk ke konteks LLM. | Reranking dipakai untuk meningkatkan presisi setelah kandidat dikumpulkan. Jika reranker model tidak aktif, sistem tetap berjalan memakai RRF score. |
| 12 | **Domain Metadata Boosting** | `backend/app/core/rag/engine/rankers.py` | `query_metadata_boost(query, metadata, text)` | Memberi boost pada chunk berdasarkan metadata hukum/domain seperti pasal, ayat, bab, dokumen, indikator, dan konteks regulasi. | Dipilih karena domain SPBE sangat bergantung pada struktur dokumen. Metadata boosting membantu chunk legal yang tepat naik ranking walaupun skor semantik tidak paling tinggi. |
| 13 | **Structured Fact Fallback** | `backend/app/core/rag/structured_facts.py` | `find_structured_fact_answer(query, min_score=0.72)` | Menjawab pertanyaan faktual yang sangat mirip dengan daftar fakta curated. | Dipilih untuk menangani pertanyaan benchmark/faktual yang membutuhkan jawaban sangat presisi, seperti definisi, angka, tabel, atau entitas yang rawan hilang di retrieval umum. |
| 14 | **Context Formatter** | `backend/app/core/rag/langchain_engine.py` | `_format_context(final_docs)` | Mengubah dokumen hasil retrieval menjadi konteks bernomor untuk LLM. | Diperlukan agar LLM menerima konteks yang rapi, terstruktur, dan bisa dirujuk melalui sitasi `[1]`, `[2]`, dst. |
| 15 | **Source Builder / Source Cards** | `backend/app/core/rag/langchain_engine.py`, `backend/app/core/formatting.py` | `_build_sources_list(final_docs)`, `filter_used_sources`, `renumber_citations_and_sources` | Membuat daftar sumber yang ditampilkan ke frontend dan menyelaraskan citation ID. | Dipilih agar pengguna bisa melihat sumber dokumen yang benar-benar dipakai, bukan semua hasil retrieval mentah. Ini penting untuk trust dan auditability. |
| 16 | **Citation Sanitizer & Renumbering** | `backend/app/core/formatting.py` | `sanitize_citations`, `filter_used_sources`, `renumber_citations_and_sources`, `append_citation_reference_block` | Membersihkan citation invalid dan mengurutkan citation user-facing menjadi `[1]`, `[2]`, `[3]`. | Dipilih karena format citation yang loncat seperti `[4]`, `[2]`, `[5]` membingungkan user. Renumbering membuat tampilan seperti gaya IEEE dan lebih mudah dibaca. |
| 17 | **Answer Grounding Validation / LLM09 Guardrail** | `backend/app/core/rag/prompts.py`, `backend/app/api/routes/chat.py` | `validate_answer(answer, context, sources)`. Wajib inline citation; cek citation number; cek hallucinated Pasal/Ayat; cek metadata mismatch. | Memvalidasi apakah jawaban benar-benar grounded pada konteks dan citation. | Dipilih untuk memenuhi kebutuhan utama produk: jawaban harus terverifikasi dan bersumber. Ini juga mendukung mitigasi OWASP LLM09 misinformation. |
| 18 | **Safe Fallback untuk Jawaban Tidak Valid** | `backend/app/api/routes/chat.py` | `_build_llm09_safe_fallback(validation)` | Mengganti jawaban yang gagal validasi dengan pesan aman. | Dipilih agar sistem tidak tetap mengirim jawaban yang tidak bisa diverifikasi. Ini penting untuk domain regulasi dan audit. |
| 19 | **Insufficient Context Fallback** | `backend/app/api/routes/chat.py` | `_build_llm09_insufficient_context_answer()` | Mengembalikan jawaban fail-closed jika konteks dokumen tidak cukup. | Dipilih untuk menghindari hallucination ketika retrieval tidak menemukan bukti yang memadai. |
| 20 | **LLM01 Prompt Injection Guardrails** | `backend/app/core/rag/guardrails.py`, `backend/app/core/rag/output_guardrails.py`, `backend/app/api/routes/chat.py` | Deteksi prompt injection, unsafe output, system prompt leak, secret leak, internal tool leak. | Mencegah input/output berbahaya memengaruhi sistem atau membocorkan instruksi internal. | Dipilih karena chatbot berbasis dokumen rentan terhadap prompt injection, terutama jika dokumen atau user prompt mengandung instruksi berbahaya. |
| 21 | **LLM08 Retrieval Access Control** | `backend/app/core/rag/access_control.py`, `backend/app/core/rag/engine/retrievers.py`, `backend/app/core/rag/engine/context_stitching.py` | Role aktif: `admin_pusdatik`, `staff`. `DEFAULT_ALLOWED_ROLES=["admin_pusdatik", "staff"]`. Fail-closed memakai `__spbe_no_matching_role__`. | Memastikan retrieval Qdrant, BM25, literal search, context stitching, dan citation API hanya mengembalikan chunk yang boleh diakses user. | Dipilih untuk mencegah unauthorized retrieval dan citation leak, sesuai OWASP LLM08 Vector and Embedding Weaknesses. |
| 22 | **Document Scope Filter** | `backend/app/core/rag/access_control.py`, `backend/app/core/rag/langchain_engine.py` | `build_qdrant_access_filter(doc_id, current_user)` | Membatasi retrieval ke dokumen tertentu jika user memilih `document_id`. | Dipilih untuk mencegah cross-document contamination ketika user ingin bertanya pada satu dokumen spesifik. |
| 23 | **Chat Request Bounds** | `backend/app/models/schemas.py` | `message` max 5000 chars, `top_k` 1–20, `max_tokens` 128–4096, `max_quality_retries` 0–3 | Membatasi input dan parameter retrieval/generation. | Dipilih untuk menjaga performa, mengurangi abuse, dan membuat workload retrieval/LLM lebih deterministik. |
| 24 | **Chunking Strategy Umum** | `backend/app/config.py`, `backend/app/core/ingestion/structured_chunker.py` | `CHUNK_SIZE=600`, `CHUNK_OVERLAP=100`, `MIN_CHUNK_SIZE=80`, `MAX_CHUNK_SIZE=600` | Memecah dokumen menjadi chunk standar. | Dipilih agar chunk cukup kecil untuk retrieval presisi, tetapi masih menyimpan konteks yang cukup untuk jawaban. |
| 25 | **Chunking Peraturan** | `backend/app/config.py`, `backend/app/core/ingestion/structured_chunker.py` | `CHUNK_SIZE_PERATURAN=900`, `CHUNK_OVERLAP_PERATURAN=150` | Chunk khusus dokumen regulasi/peraturan. | Dokumen peraturan membutuhkan chunk lebih besar agar pasal/ayat tidak terlalu terpecah dan konteks hukum tetap utuh. |
| 26 | **Chunking Laporan** | `backend/app/config.py`, `backend/app/core/ingestion/structured_chunker.py` | `CHUNK_SIZE_LAPORAN=1800`, `CHUNK_OVERLAP_LAPORAN=200` | Chunk khusus dokumen laporan/audit. | Laporan biasanya berbentuk narasi panjang, sehingga chunk lebih besar membantu mempertahankan konteks paragraf dan analisis. |
| 27 | **OCR Pipeline** | `backend/app/config.py`, `backend/app/core/ingestion` | `OCR_ENGINE="paddleocr"`, `OCR_LANG="id"`, `OCR_USE_GPU=True` | Mengekstrak teks dari PDF yang tidak text-selectable. | Dipilih agar sistem tetap bisa mengindeks dokumen hasil scan atau PDF yang membutuhkan OCR. Bahasa `id` dipakai karena dokumen dominan Bahasa Indonesia. |
| 28 | **Document Manager / Indexing Pipeline** | `backend/app/core/ingestion/document_manager.py` | Maksimal indexing: `MAX_INDEX_CHUNKS=10000`; index ke Qdrant dan BM25; rebuild BM25 setelah indexing. | Mengelola upload, parsing, chunking, indexing, dan rebuild index. | Dipilih agar lifecycle dokumen terpusat dan Qdrant/BM25 tetap sinkron setelah dokumen ditambah/dihapus. |
| 29 | **RAGAS Evaluation Framework** | `backend/scripts/evaluate_ragas.py`, `backend/data/*ragas*` | RAGAS 0.2.x, mendukung judge Groq/OpenAI/Ollama, metrik seperti context precision, context recall, faithfulness, answer relevancy. | Mengevaluasi kualitas RAG secara offline. | Dipilih karena RAGAS dapat mengukur kualitas retrieval dan kualitas jawaban, bukan hanya manual testing. |
| 30 | **LLM08 Evidence Audit** | `backend/scripts/llm08_evidence_audit.py`, `backend/reports/llm08/llm08_evidence_audit.md` | Evidence terakhir: unauthorized retrieval 0 leaked items, citation leak rate 0.0%, SQLite/BM25/Qdrant metadata completeness 100%, malicious chunk PASS. | Membuktikan retrieval isolation dan metadata completeness. | Dipilih agar klaim keamanan LLM08 tidak hanya konseptual, tetapi punya bukti uji berbasis skenario. |
| 31 | **LLM09 Misinformation Evaluation** | `backend/scripts/llm09_misinformation_eval.py`, `backend/tests/test_llm09_misinformation*.py`, `backend/reports/llm09/*` | Fixture adversarial LLM09, evaluator deterministic, optional live collector. | Menguji apakah sistem menolak/mengoreksi jawaban yang tidak grounded. | Dipilih karena sistem digunakan untuk jawaban regulasi yang harus bisa dipertanggungjawabkan. |
| 32 | **Debug Retrieval Endpoint** | `backend/app/api/routes/chat.py` | `GET /api/chat/debug/retrieval`, admin-only via `require_roles(["admin_pusdatik"])` | Melihat query type, source count, dan raw retrieved docs. | Dipilih untuk auditability dan troubleshooting retrieval tanpa menebak isi konteks yang dipakai sistem. |
