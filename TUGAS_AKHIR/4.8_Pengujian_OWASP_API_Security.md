# BAB 4.8: RANCANGAN PENGUJIAN KEAMANAN API BERDASARKAN OWASP API SECURITY TOP 10 2023

## 4.8.1 Latar Belakang Pengujian Keamanan API

Sistem Asisten Cerdas RAG-SPBE PUSDATIK BSSN dibangun di atas arsitektur berbasis REST API yang mengekspos sejumlah endpoint untuk keperluan autentikasi, pengajuan pertanyaan ke chatbot, pengelolaan knowledge base, dan pencatatan audit. Meskipun sistem ini beroperasi di lingkungan jaringan internal BSSN dan hanya dapat diakses oleh pegawai yang terautentikasi, ancaman keamanan API tetap perlu ditangani secara sistematis. Risiko tidak selalu berasal dari penyerang eksternal, melainkan juga dari potensi penyalahgunaan akses oleh pengguna internal yang memiliki kredensial valid namun mencoba mengakses resource di luar kewenangannya.

Lapisan autentikasi yang diimplementasikan menggunakan JSON Web Token (JWT) dengan integrasi LDAP/Active Directory, mekanisme Policy-Based Access Control (PBAC), token blacklist, dan rate limiting, seluruhnya harus diuji ketahanannya terhadap kerentanan-kerentanan yang terdokumentasi dalam standar industri. Standar yang digunakan sebagai kerangka acuan pada penelitian ini adalah **OWASP API Security Top 10 versi 2023**, yang diterbitkan oleh *Open Web Application Security Project* sebagai referensi risiko keamanan API paling kritis dan paling sering ditemukan pada sistem berbasis web modern.

## 4.8.2 OWASP API Security Top 10 2023: Pengertian dan Relevansi

OWASP API Security Top 10 2023 merupakan pembaruan dari versi 2019 yang memperkenalkan kategorisasi risiko yang lebih spesifik terhadap pola serangan API modern. Berbeda dengan OWASP Top 10 untuk aplikasi web umum, standar ini difokuskan pada kerentanan yang spesifik muncul pada desain dan implementasi API — khususnya REST API yang menggunakan JSON sebagai format pertukaran data dan JWT sebagai mekanisme autentikasi.

Tabel 4.X berikut menampilkan seluruh kategori OWASP API Security Top 10 2023 beserta penjelasan singkat dan penilaian relevansinya terhadap sistem yang dibangun pada penelitian ini.

**Tabel 4.X Pemetaan Kategori OWASP API Security Top 10 2023 terhadap Sistem RAG-SPBE**

| Kode | Nama Kategori | Deskripsi Singkat | Relevansi pada Sistem |
|---|---|---|---|
| **API1:2023** | Broken Object Level Authorization (BOLA) | API tidak memvalidasi apakah pengguna berhak mengakses objek tertentu berdasarkan identitasnya | **Relevan** — Sistem memiliki endpoint audit log dan riwayat sesi chat yang dapat diakses dengan parameter `username` dan `session_id` |
| **API2:2023** | Broken Authentication | Kelemahan pada mekanisme autentikasi token, termasuk algoritma JWT yang lemah, token tanpa kedaluwarsa, dan tidak adanya perlindungan brute force | **Relevan** — Sistem menggunakan JWT dengan algoritma HS256; risiko mencakup serangan `alg:none`, manipulasi payload, brute force login, dan replay attack |

| **API10:2023** | Unsafe Consumption of APIs | Sistem mengonsumsi API pihak ketiga tanpa validasi response yang memadai, sehingga data berbahaya dari layanan eksternal dapat memengaruhi logika aplikasi | **Relevan Informasional** — Sistem mengonsumsi LDAP/AD untuk autentikasi dan Ollama untuk inferensi LLM; keduanya perlu menangani error dan timeout dengan benar |

## 4.8.3 Konteks Kerawanan pada Sistem

Sebelum mendefinisikan skenario pengujian, perlu dipahami mengapa masing-masing kategori OWASP relevan dalam konteks spesifik sistem RAG-SPBE ini. Berikut penjelasan kontekstual untuk setiap kategori yang diuji secara aktif.

### 4.8.3.1 Konteks API1:2023 — BOLA pada Sistem Multi-Pengguna

Sistem RAG-SPBE dirancang untuk digunakan oleh beberapa pengguna secara bersamaan dengan role yang berbeda (`evaluator_spbe`, `staf_pusdatik`, `admin_pusdatik`). Setiap pengguna memiliki riwayat sesi chat (`session_id`) dan data audit yang terkait dengan identitasnya. Risiko BOLA muncul ketika API tidak memvalidasi kepemilikan objek — misalnya, apakah `session_id` yang dikirimkan dalam request benar-benar milik pengguna yang membuat request tersebut.

Pada sistem ini, dua titik potensi BOLA diidentifikasi:

1. **Endpoint `/api/audit/logs`** — menerima parameter `username` sebagai filter. Jika tidak ada validasi bahwa pengguna hanya boleh melihat log miliknya sendiri (kecuali admin), pengguna A dapat mengirim parameter `username=pengguna_b` untuk melihat aktivitas pengguna lain.

2. **Endpoint `/api/chat/query`** — menerima `session_id` sebagai bagian dari request. Jika sistem tidak memvalidasi bahwa `session_id` yang dikirimkan milik pengguna yang sedang aktif, pengguna dapat mencoba menebak atau memanipulasi `session_id` untuk mengakses konteks percakapan pengguna lain.

### 4.8.3.2 Konteks API2:2023 — Broken Authentication pada JWT

JWT merupakan inti dari mekanisme autentikasi sistem ini. Kerentanan autentikasi pada JWT dapat terjadi dalam beberapa bentuk yang berbeda:

**a. Serangan `alg:none` (Algorithm Confusion)**
JWT terdiri dari tiga bagian: header, payload, dan signature yang dipisahkan titik. Header JWT berisi klaim `alg` yang menentukan algoritma penandatanganan. Kerentanan muncul ketika implementasi server menerima nilai `alg: none` — artinya server tidak memverifikasi signature sama sekali. Penyerang dapat memodifikasi payload JWT (misalnya mengubah `roles` menjadi `admin_pusdatik`) lalu menghapus signature dan mengubah header menjadi `alg: none`. Jika server menerimanya, penyerang mendapatkan akses tidak sah dengan privilege tertinggi.

Pada sistem ini, kerentanan ini dimitigasi dengan parameter `algorithms=["HS256"]` pada fungsi `jwt.decode()` — daftar eksplisit yang menolak nilai `none`. Pengujian dilakukan untuk memverifikasi bahwa mitigasi ini berfungsi.

**b. Manipulasi Payload (Token Forgery)**
Penyerang yang berhasil mendapatkan token valid dapat mencoba memodifikasi bagian payload (misalnya mengubah `"roles": ["evaluator_spbe"]` menjadi `"roles": ["admin_pusdatik"]`) tanpa memiliki secret key. Perubahan sekecil apapun pada payload akan membuat HMAC-SHA256 signature tidak cocok dengan payload baru, sehingga verifikasi gagal. Pengujian ini memvalidasi bahwa integritas signature diverifikasi dengan benar.

**c. Brute Force pada Endpoint Login**
Tanpa mekanisme pembatasan percobaan, penyerang dapat mengirimkan ribuan request login dengan kombinasi password berbeda secara otomatis (*credential stuffing* atau *password spraying*). Sistem ini mengimplementasikan rate limiting berbasis IP dan username pada endpoint `/api/auth/login` untuk menanggulangi hal ini.

**d. Replay Attack (Penggunaan Token Pasca-Logout)**
Setelah pengguna melakukan logout, token JWT yang pernah diterbitkan masih memiliki masa berlaku tersisa. Tanpa mekanisme blacklist, token tersebut dapat digunakan kembali oleh pihak yang berhasil mencurinya. Sistem mengimplementasikan blacklist `jti` (JWT ID) di SQLite untuk mencegah replay attack.

### 4.8.3.3 Konteks API3:2023 — Data Eksposur pada Response API

Kerentanan ini tidak selalu berasal dari serangan aktif, melainkan dari desain API yang mengembalikan lebih banyak data dari yang diperlukan. Pada sistem ini, dua aspek diperiksa:

1. **Excessive Data Exposure** — Response endpoint `/api/auth/login` diperiksa apakah mengandung field sensitif seperti `hashed_password`, nilai `jti` token internal, atau detail konfigurasi sistem yang tidak diperlukan oleh klien.

2. **Mass Assignment** — Penyerang mengirimkan field tambahan dalam body request (misalnya `"roles": ["admin_pusdatik"]`, `"is_admin": true`) dengan harapan server menerima dan menerapkan nilai tersebut. Pydantic schema validation pada FastAPI menangani ini dengan menolak field yang tidak terdefinisi dalam model.

### 4.8.3.4 Konteks API4:2023 — Konsumsi Sumber Daya Berlebihan

Endpoint `/api/chat/query` adalah endpoint paling intensif secara komputasi karena setiap request memicu pipeline RAG yang mencakup:
- Embedding query pengguna
- Pencarian hybrid di Qdrant dan BM25
- Reranking hasil retrieval
- Inferensi model LLM melalui Ollama

Tanpa pembatasan, satu pengguna dapat mengirimkan puluhan request per detik, menghabiskan sumber daya server dan berpotensi melumpuhkan layanan bagi pengguna lain (*Denial of Service* berbasis resource exhaustion). Rate limiting dikonfigurasi 60 request/menit per pengguna untuk endpoint ini. Selain itu, payload request yang sangat besar (misalnya pertanyaan sepanjang jutaan karakter) juga dapat menjadi vektor serangan.

### 4.8.3.5 Konteks API5:2023 — BFLA pada Sistem PBAC

Sistem mengimplementasikan tiga level role dengan hak akses yang berbeda. Kerentanan BFLA terjadi ketika deklarasi role tidak diterapkan secara konsisten pada setiap endpoint. Pada sistem ini, endpoint berikut memiliki pembatasan role yang harus diverifikasi:

| Endpoint | Role yang Diperlukan | Risiko Jika Tidak Diverifikasi |
|---|---|---|
| `/api/knowledge-base/upload` | `admin_pusdatik` | Pengguna biasa dapat menyuntikkan dokumen berbahaya ke knowledge base |
| `/api/audit/logs` | `admin_pusdatik` | Pengguna biasa dapat membaca seluruh log aktivitas pengguna lain |
| `/api/auth/force-logout` | `admin_pusdatik` | Pengguna biasa dapat memaksa pengguna lain logout |
| `/api/chat/query` | Semua role terautentikasi | Tanpa token, siapa pun dapat mengakses chatbot |

### 4.8.3.6 Konteks API8:2023 — Security Misconfiguration

Konfigurasi yang tidak tepat dapat membuka celah yang tidak terlihat pada level kode. Pada sistem ini, tiga aspek diperiksa:

1. **Konfigurasi CORS** — Jika `Access-Control-Allow-Origin` diset ke `*` (wildcard), halaman web dari domain mana pun dapat mengirimkan request ke API dan membaca responsenya. Sistem harus membatasi CORS hanya ke domain frontend yang resmi.

2. **HTTP Security Headers** — Header seperti `X-Frame-Options`, `X-Content-Type-Options`, dan `Strict-Transport-Security` memberikan lapisan perlindungan tambahan di level browser. Ketiadaan header-header ini meningkatkan risiko clickjacking dan MIME sniffing.

3. **Verbositas Pesan Error** — Pesan error yang terlalu detail (mengandung stack trace, nama library, atau query database) dapat memberikan informasi berharga bagi penyerang untuk memahami arsitektur internal sistem.

### 4.8.5.1 Burp Suite Community Edition

Burp Suite dikembangkan oleh PortSwigger dan merupakan standar industri pengujian keamanan aplikasi web. Cara kerjanya adalah menempatkan diri sebagai *proxy* antara browser penguji dan server target sehingga seluruh traffic HTTP dapat diinspeksi dan dimodifikasi. Pada penelitian ini, dua komponen Burp Suite yang digunakan adalah **Repeater** untuk mengirimkan request yang telah dimodifikasi secara manual (skenario BOLA dan Broken Object Property Level Authorization) dan **Decoder** untuk melakukan decode/encode komponen JWT dalam format Base64URL.

### 4.8.5.2 jwt_tool

jwt_tool adalah *command-line tool* berbasis Python yang dikembangkan khusus untuk pengujian keamanan JWT. Tool ini mengotomasi proses manipulasi token yang kompleks — termasuk serangan `alg:none` — dengan menghasilkan token hasil modifikasi dalam format yang valid secara sintaksis. Perintah utama yang digunakan adalah `python jwt_tool.py <TOKEN> -X a` untuk mengeksekusi serangan `alg:none` secara otomatis.

### 4.8.5.3 Apache JMeter

Apache JMeter dikembangkan oleh Apache Software Foundation sebagai *open-source load testing tool*. JMeter mensimulasikan banyak pengguna virtual (*thread*) yang mengirimkan request secara bersamaan ke endpoint target. Dalam penelitian ini, JMeter digunakan untuk mengirimkan request ke `/api/chat/query` secara masif guna mengukur pada titik mana server mengaktifkan mekanisme rate limiting dan mengembalikan response 429 Too Many Requests.

### 4.8.5.4 Postman

Postman adalah *API testing client* berbasis GUI yang memungkinkan pengelolaan koleksi request secara terstruktur. Fitur *Environment* pada Postman digunakan untuk menyimpan token JWT dari masing-masing role (`evaluator_spbe`, `staf_pusdatik`, `admin_pusdatik`) sebagai variabel yang dapat dipilih secara cepat, sehingga pengujian BFLA lintas role dapat dilakukan secara sistematis dan terulang.

### 4.8.5.5 OWASP ZAP (Zed Attack Proxy)

OWASP ZAP dikembangkan dan dikelola langsung oleh OWASP Foundation, menjadikannya referensi tools yang paling tepat untuk memvalidasi implementasi terhadap standar OWASP itu sendiri. Fitur **Passive Scan** pada ZAP menganalisis seluruh response HTTP secara otomatis dan menghasilkan laporan *Alert* yang dikategorikan berdasarkan tingkat risiko (High, Medium, Low, Informational), mencakup header keamanan yang tidak hadir, konfigurasi CORS yang bermasalah, dan informasi internal yang terekspos.

## 4.8.6 Batasan Pengujian

Pengujian keamanan pada penelitian ini dilakukan dalam beberapa kondisi dan batasan berikut:

1. **Lingkungan pengujian** — Seluruh skenario dilaksanakan pada lingkungan pengembangan lokal (*localhost*) dengan konfigurasi yang setara dengan spesifikasi produksi, kecuali pada aspek HTTPS. Pengujian di lingkungan lokal tidak menggunakan TLS/HTTPS sehingga aspek keamanan transport tidak dapat diuji secara langsung.

2. **Cakupan kategori** — Dari sepuluh kategori OWASP API Security Top 10 2023, delapan kategori dikaji dalam penelitian ini. Dua kategori (API9 dan API10) bersifat informasional dan hanya diobservasi tanpa skenario eksploitasi aktif.

3. **Fokus pada lapisan autentikasi** — Pengujian diprioritaskan pada kerentanan yang berkaitan langsung dengan implementasi JWT, PBAC, rate limiting, dan konfigurasi keamanan API, sebagaimana yang menjadi kontribusi utama penelitian ini. Kerentanan pada lapisan logika bisnis RAG (misalnya prompt injection) berada di luar cakupan pengujian ini.

4. **Etika pengujian** — Seluruh pengujian dilakukan pada sistem milik peneliti sendiri dalam lingkungan yang terkontrol dan tidak melibatkan infrastruktur produksi BSSN maupun data pengguna nyata.
